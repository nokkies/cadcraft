## 0.112  2026-10-18  New check M4-C22 measures the height every text RENDERS at; it fails GAD-001, and writing it took three attempts because each version was vacuous in a different way
Changed: psa/scripts/check-textheights.ps1 (M4-C22) added and wired into gen-all's $checks, and gen-all now carries a named list of known accepted exceptions so a new failure is never mistaken for a standing one. Neither audit is wrong; the height that renders lives on the attribute's own text properties, in the seam between them. Two checks that each cover a layer of a structure, and the value that matters sits between them.
Check:   the honest part is that three successive versions of this check passed all twelve sheets while the defect it was written for was present. Version one read height off the attribute itself, where it is always null, so it compared zero attributes on every sheet and printed twelve green lines -- it also flagged four sheets for the rail-lengths note and draft stamps the generators add on purpose, which is what a plain multiset comparison does to intentional additions. Verified both ways: a corrupted payload (one balloon height set to 99.0) reports mismatches, and the clean run reports 11 PASS with GAD-001 failing on attribute height 2.5 (source 98, generated 73) and 15.0 (source 0, generated 25). The check also fails a sheet that has attributes but whose comparison sees none, so a null-field regression cannot hide behind a green line. gen-all now exits 1 for this; the failure is GAD-001's true state, recorded rather than suppressed, and is the second named accepted exception alongside SCD-002 TX1.

## 0.111  2026-10-18  The GAD-001 ink excess is explained: TrueType attribute text inside a scaled block renders 1.25x too large, and it is the one sheet whose balloons use a tahoma style
Changed: no behaviour change, one upstream note. Build 0.110 left generated sheets plotting at 1.00 to 1.08 times the source's ink and the excess was unexplained. Traced to the end. The _TagCircle balloon block is inserted 25 times at scale 6.0 on GAD-001 in both source and generated, with identical block definitions and identical reference scales, and its text uses style ISOCP which resolves to tahoma.ttf with trueType true. Measured on the plotted PDFs the balloon circles are 9.98mm in the source and 12.51mm in the generated sheet -- ratio 1.253, uniform across all 25. Extracted text sizes agree: the generated sheet reports 4 spans at 8.62mm where the source has nothing above 1.15mm, and the issued reference plots have no text above 4mm anywhere, so 8.62mm is out of family. Across all twelve sheets exactly one mismatches: GAD-001 (ISOCP/tahoma) comes back 2.5 -> 15.0, while the eleven sheets whose balloons use isocp2.shx reproduce 2.0, 3.0 and 5.0 exactly. So the TrueType path multiplies the enclosing INSERT scale into an attribute height where the stroke path does not. A synthetic test on the template's empty model space confirms it: text at height 2.5 drawn directly measures 2.50, the same text inside _TagCircle at scale 6 measures 15.00.
Check:   the claim is bounded deliberately. What is measured is that identical drawing data yields balloons 1.25x larger in the generated plot, and that the effect tracks the TrueType style rather than the geometry. What is NOT claimed is that AutoCAD's output is the reference for which size is correct -- cadcraft cannot read SHX, so the source's isocp2 balloons are themselves rendered with cadcraft's stroke font and are not what AutoCAD would draw either. What holds up is the internal inconsistency: two paths that should agree do not. This also corrects colour-stroke-fidelity.md, which had already spotted these same balloon glyphs and attributed them to SHX substitution; ISOCP is TrueType, rendered natively and never substituted, and the real mechanism is a scale interaction. ## 0.103  2026-10-18  Saveas viewport defect localised by differential test: it is the DWG bridge, and there is no renumbering routine to fix
Changed: acted on round 41's finding -- the erased detail viewports are a real visual loss (6,329 stroked items in the source's bottom-left cell vs 0 generated), and the thing forcing the erase is the saveas viewport defect. So went after the defect itself, and localised it by differential test rather than by reading code. Same template, same layout.set + saveas, two targets: saving to .dxf leaves 41D1 at id=1 (correct); saving to .dwg moves it to id=3, promoting a sheet viewport into a model window. The DXF path is innocent at both ends -- dxf_write.rs:1059 writes w.i(69, i64::from(v.id)) verbatim and dxf_read.rs:490 reads id: t.i(69).unwrap_or(0) as u32, and a DXF round-trip preserves all four ids exactly. The DWG path loses them because DWG HAS NO VIEWPORT-ID FIELD: converting the saved DWG back to DXF yields VIEWPORT records with group 69 = 1,2,3,4 in record order, i.e. sequential numbering by position. crates/dwg/src/lib.rs is a 456-line entity-type map with no viewport case, and dxf_write.rs:1436-1439 already documents it: "DWG does not store viewport ids; readers number them in order." THE IMPORTANT CORRECTION: the note said the fix is in "the save-time id renumbering", which implies a renumbering routine that should stop -- there is no such routine. The real problem is that the sheet/model distinction has nowhere to live across a DWG save, so the fix is to preserve the distinction, either by deriving it on read (viewCenter == center and viewHeight == height means sheet window, give it id 1) or by storing it the way paper_view already does for DXF via CADCraft xdata (dxf_write.rs:1459-1462). Deriving from geometry is attractive: no format extension, and it works on files written by other applications. Also found while testing: my own repro failed three times for PowerShell quoting reasons (ConvertTo-Json on a bare path string, and backslash escaping) and I nearly read those as cadcraft defects -- the fix was building the script line with explicit quoting, after which saveas wrote 174,739 bytes cleanly.
