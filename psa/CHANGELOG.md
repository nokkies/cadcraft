## 0.088  2026-10-18  Colour audit added and run on all twelve sheets; the large mismatches were my own render-scale artifact
Changed: build 0.087 measured colour on one sheet and generalised, which was not safe -- a colour bug on any other sheet would have been missed. Added psa/scripts/audit-colours.ps1 and ran it across all twelve. It converts source and generated to SVG (each stroke keeps its colour, width and coordinates as text, so no vision model is involved) and fails if any stroke above a glyph-sized span is absent from the generated sheet, or if any colour has FEWER strokes than the source. The decisive detail is that both files must be rendered through the SAME explicit window: without it each is auto-fitted to its own zoom, the two SVGs get different viewBox sizes, and every coordinate becomes incomparable. That is not hypothetical -- the first unconstrained pass reported 1,525 large mismatches on GAD-001 including border-sized spans of 800 and 1000 units, and 93 on SCD-002, all of it pure scale. With both viewBoxes pinned to 2100x1400, SCD-002's 93 fall to 0 and GAD-001's 1,525 to 214. Distinguishing present-but-moved from genuinely lost, by matching shape independently of position: all 214 GAD-001 mismatches have their exact shape present in the generated file and only their position differs -- magenta (text), span exactly 9.0, at x positions about 11 apart. That is character advance width, the defect in shx-font-width.md, now confirmed geometrically rather than by counting words. The audit is standalone like audit-layers, audit-linetypes and audit-sheet-space: these are slow full-corpus comparisons, while gen-all holds the fast per-build checks.
Check:   audit-colours.ps1: exit 0 on all 12 sheets, 0 non-glyph strokes lost anywhere, no colour with fewer strokes than source. Per-sheet unmatched strokes above 5 units: GAD-001 214 (all present-but-moved), every other sheet 0. Stroke width identical on both sides of every sheet (1.400000 at the fixed window). Colour counts identical on the eight sheets whose polyline counts match; SCD-003/004/005 and GAD-001 carry more, which is the known D4/D3 additions. viewBox guard verified to fire when the window is not pinned. Full gen-all: exit 0, all 20 checks green.

## 0.085  2026-10-18  Linetype audit extended: header variables match, and dashes proved to scale with zoom
Changed: added two more checks to psa/scripts/audit-linetypes.ps1, for the two remaining ways dash density can look wrong while every entity and layer still matches. (1) HEADER VARIABLES: LTSCALE multiplies every dash length, PSLTSCALE makes dash density depend on viewport zoom, CELTSCALE and LWDISPLAY do the same for the current entity and for lineweights -- none of these appear on any entity, so no earlier audit could see them. Read with getvar and compared per sheet: all twelve match their source on LTSCALE, PSLTSCALE, CELTSCALE, LWDISPLAY and MEASUREMENT (LTSCALE 1.0, PSLTSCALE 1, MEASUREMENT 1). (2) ZOOM SCALING: PSLTSCALE=1 means paper-space viewports scale dashes by their zoom, so the content-viewport framing the generators pick could in principle change how dense dashes look. Settled by rendering the same HIDDEN line through windows 400 and 100 units wide -- the same image, 4x the pixels per unit -- and taking the ratio of mean dash length. cadcraft scales dashes in drawing units, so framing does not change dash density.

## 0.076  2026-10-18  FONTALT substitution: SHX text renders in a real TTF in the review PDFs
Changed: the "worse than originals" render (build 0.074/0.075) traced to cadcraft substituting its stroke font for the 99/99 isocp.shx texts. Found cadcraft's intended lever: TextFont::resolve (crates/fonts/src/lib.rs:287-295) -- for a font it cannot find (an SHX file) it renders in the FONTALT font (CADCRAFT_FONTALT) when that names a findable face, else the stroke font. cadcraft scans C:\Windows\Fonts, so arial.ttf is findable. Set CADCRAFT_FONTALT=arial.ttf (configurable, -FontAlt, default arial.ttf, '' = stroke font) in the three scripts that export the review PDFs (export-pdf.ps1, check-f5.ps1, check-ink.ps1) so the plotted PDFs render SHX text in a real TrueType face instead of the stroke font. Verified end-to-end: the env var inherits through the .cmd -> cmd.exe -> cadcraft-cli chain the scripts use; the exportpdf hash changes with FONTALT; the rendered PDF text is crisp TrueType with no overruns and the title block fits its cells. Honest scope: this improves render QUALITY (real font outlines, not stroke sticks) but does NOT make text metrically match isocp -- Arial advance widths differ from isocp, so the SHX advance-width gap (psa/pr/shx-font-width.md) remains; the DWG data is unchanged (AutoCAD still opens the sheet with the real isocp.shx). Clean-room safe: no font is shipped, cadcraft uses a face already on the user's machine.
Check:   full gen-all with FONTALT=arial: exit 0, all 19 checks green (check-f5: 12 distinct non-empty PDFs; check-ink: all monochrome, Arial is black-on-white). Rendered SCD-001 PDF at 2x: text crisp, no overruns, title-block cells fit.
